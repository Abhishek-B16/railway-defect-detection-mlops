1. EXECUTIVE SUMMARY & HIGH-LEVEL ARCHITECTURE
--------------------------------------------------------------------------------
RailGuard is an industrial-grade Machine Learning Operations (MLOps) platform
designed to automate visual railway defect detection. 

Traditional rail inspection relies on human trackmen walking miles of railway
tracks, which is slow, hazardous, and prone to fatigue. RailGuard provides
automated anomaly detection using computer vision, fine-tuned YOLOv8 deep learning
models, and a containerized microservice architecture.

The System Architecture covers the complete MLOps lifecycle:
1. Data Versioning: DVC (Data Version Control) + DagsHub Cloud Storage.
2. Experiment Tracking: DagsHub hosted MLflow tracking metrics (mAP50, Box Loss).
3. Model Governance: MLflow Model Registry with dynamic '@candidate' alias tagging.
4. Serving Layer: Decoupled FastAPI microservice (Dockerized).
5. Operational UI: React.js (Vite) dashboard with HTML5 dynamic canvas overlays.
6. Observability: Prometheus (/metrics) + Grafana real-time telemetry dashboards.

3. THE 6 RAILWAY DEFECT CLASSES EXPLAINED (DEEP DIVE)
--------------------------------------------------------------------------------

1. CRACK:
   - What it is: Transverse, longitudinal, or vertical fractures through the steel.
   - Danger: Immediate derailment risk if the rail breaks under axle loads.

2. BOLTS (Fasteners):
   - What it is: Fishplate bolts, tie-plate clips, and track anchoring bolts.
   - Danger: Missing or loose bolts cause rail joints to separate and track gauge
     to widen, leading to train derailment.

3. JOINTS (Fishplates):
   - What it is: Mechanical connection points where two rail segments join.
   - Danger: Misaligned or battered joints cause high impact wheel stress and
     joint bar fractures.

4. FLAKING:
   - What it is: Shallow surface metal peeling off in thin, fish-scale layers
     (1 mm to 2 mm deep) along the running band.
   - Cause: Work hardening and Rolling Contact Fatigue (RCF).
   - Maintenance: Preventive rail grinding removes the layer before it cracks.

5. SHELLING:
   - What it is: Severe, deep subsurface horizontal cracking that causes large
     chunks of metal to break away along the gauge corner.
   - Danger: Severe degradation requiring immediate rail segment replacement.

6. SPALLING:
   - What it is: Pitting and crater-like cavities breaking out on the rail surface.
   - Cause: Cyclic micro-cracking combining under heavy repetitive axle pressure.

Summary Comparison:
- Flaking  = Shallow surface peeling (early warning).
- Spalling = Medium depth craters and pits.
- Shelling = Deep structural gouging along the gauge corner.

5. FRONTEND ARCHITECTURE (REACT, VITE, HTML5 CANVAS)
--------------------------------------------------------------------------------
- Stack: React 18, Vite build tool, Lucide React icons, Vanilla CSS.
- Decoupled Design: The frontend has ZERO machine learning libraries. It is a
  pure presentation client that communicates with FastAPI via standard HTTP REST.
- Dynamic Canvas Overlay Engine:
  Uploaded images vary in native resolution (e.g. 1920x1080) compared to screen
  display size (e.g. 500x350). The React client dynamically calculates:
    scaleX = clientWidth / naturalWidth
    scaleY = clientHeight / naturalHeight
  It scales the bounding box coordinates (x1, y1, x2, y2) and renders crisp,
  color-coded boxes on top of the image using an HTML5 <canvas>.
- Resilient UI States:
  - Startup Health Check: Continuously verifies API connectivity via /health.
  - Standby State: Informs user that neural network is loaded.
  - Zero-Defect State: Shows positive confirmation when track is completely safe.
  - Error Toasting: Handles corrupt uploads or offline server states gracefully.

6. BACKEND MICROSERVICE ARCHITECTURE (FASTAPI, PYDANTIC)
--------------------------------------------------------------------------------
- Stack: FastAPI, Uvicorn (ASGI), Pydantic v2, PyTorch CPU, OpenCV (cv2), Pillow.
- Key Endpoints:
  1. POST /predict: Accepts multipart/form-data image, validates format, runs
     YOLOv8 inference, returns structured JSON:
     {
       "detections": [
         {
           "class_name": "crack",
           "confidence": 0.683,
           "bbox": { "x1": 150, "y1": 120, "x2": 240, "y2": 210 }
         }
       ]
     }
  2. GET /health: Health probe returning service name, status, and active model.
  3. GET /model-info: Returns model name, registered version, and current alias.
  4. GET /metrics: Prometheus metrics endpoint.
- Strict Pydantic Contracts:
  - HealthResponse, ModelInfoResponse, BBox, Detection, PredictionResponse.

7. MACHINE LEARNING PIPELINE (YOLOV8 & DATA-CENTRIC AI)
--------------------------------------------------------------------------------
- Backbone: Ultralytics YOLOv8 (CSPDarknet53 feature extractor + PANet neck).
- Loss Functions (Multi-Task):
  1. Complete IoU (CIoU) Box Loss: Evaluates overlap, aspect ratio, and center distance.
  2. Binary Cross-Entropy (BCE) Class Loss: Multi-label defect classification.
  3. Distribution Focal Loss (DFL): Fine-grained bounding box regression.
- Iterative Progression:
  - V1 Baseline: Raw dataset, uncleaned labels.
  - V2 Sanitization: Converted masks to bounding boxes; cleaned invalid coordinates.
  - V3 Nano: Initial baseline on 6 classes (highlighted severe 54-crack imbalance).
  - V4 Medium: Sourced & merged 718 crack images; scaled up model capacity.
  - V5 Large (Current Production): YOLOv8-Large (43M parameters) with single-block
    consolidated crack boundaries for maximum localization accuracy.

8. MLOPS ECOSYSTEM (DVC, MLFLOW, DOCKER, RENDER)
--------------------------------------------------------------------------------
- Data Version Control (DVC):
  - Manages dataset versions without storing large files in Git.
  - DVC generates 'dataset_clean.dvc' hash pointers for Git.
  - Actual image binaries are stored in DagsHub Remote Cloud Storage.
- MLflow Tracking & Model Registry:
  - Centralized tracking server hosted on DagsHub.
  - Logs training parameters, epoch-by-epoch loss curves, and validation mAP50.
  - Packaged weights (best.pt) registered as 'RailGuard-Detector' (v1-v5).
  - Deployment governed via the '@candidate' alias.
- Containerization:
  - Dockerfile.api: Python 3.10-slim with libgl1/OpenCV and CPU-optimized PyTorch.
  - docker-compose.yml: Orchestrates API, UI, Prometheus, and Grafana containers.
- Render Free Tier Cloud Optimizations:
  - Render free tier is limited to 512MB RAM.
  - Standard 640x640 inference spikes memory and causes Out-Of-Memory (OOM) crashes.
  - Optimizations: torch.set_num_threads(1), thumbnail resolution downscaling,
    and startup heap pre-allocation.

9. PRODUCTION OBSERVABILITY (PROMETHEUS & GRAFANA)
--------------------------------------------------------------------------------
- Metrics Exported via /metrics:
  - Counter: railguard_prediction_requests_total (status="success" / "failed")
  - Histogram: railguard_prediction_latency_seconds (total request latency)
  - Histogram: railguard_inference_latency_seconds (pure neural network latency)
  - Counter: railguard_detections_total (class_name="crack", "bolts", etc.)
  - Gauge: railguard_model_info (model_name, version, alias)
  - Gauge: railguard_api_health (1 = online, 0 = offline)
- Monitoring Utility:
  - Tracks API throughput and detects latency degradation.
  - Detects Concept Drift: If sudden spikes occur in specific defect classes,
    it indicates either physical track wear or camera sensor degradation.

10. TOP INTERVIEW / VIVA QUESTIONS & ANSWERS
--------------------------------------------------------------------------------

Q1: Why did you use both GitHub, DVC, and DagsHub?
A1: "GitHub is designed for code, not data; it rejects files over 100MB and suffers
     repository bloat. DVC acts as Git for data, hashing large files into tiny .dvc
     pointers. DagsHub acts as our cloud storage backend for the DVC images while
     simultaneously hosting our remote MLflow tracking server."

Q2: What is the difference between MLflow Experiments and the Model Registry?
A2: "Experiments is the research lab where we track runs, compare epoch loss curves,
     and evaluate mAP50. The Model Registry is the deployment gateway where only
     winning models are packaged into versions and assigned deployment aliases
     like '@candidate'."

Q3: Why did you choose YOLOv8 over Faster R-CNN or SSD?
A3: "YOLOv8 is an anchor-free, single-stage detector that provides superior inference
     speed and state-of-the-art accuracy (mAP50), making it ideal for real-time
     inspection feeds from drones or track inspection cars."

Q4: How do you achieve zero-downtime model updates?
A4: "Our FastAPI backend queries the MLflow Model Registry for the '@candidate' alias
     on startup. When a new model is approved, we simply reassign the '@candidate'
     tag in the registry. The API dynamically loads the new model without needing
     code modifications or server reconfiguration."

Q5: What happens if an image with no defects is uploaded?
A5: "RailGuard correctly returns 0 detections, and the frontend displays a green
     'No Defects Found! Verified Safe' confirmation. This proves the model does not
     hallucinate false positives on normal, healthy railway tracks."
